# 系统化调试

## 何时使用

- **必须**：任何技术问题——测试失败、bug、意外行为、性能问题、构建失败、集成问题，提出修复前先调用本技能
- 越是"看起来明显"、"赶时间"、"改一下就好"的时候越要用（紧急时刻最容易猜）

## 铁律

```
未完成根因调查，禁止提出修复。表象修复 = 失败。
```

## 四阶段（每阶段完成才能进入下一阶段）

### 阶段 1：根因调查

1. **完整读错误信息**——堆栈、行号、路径、错误码，别跳过
2. **稳定复现**——不能复现就收集更多数据，不猜
3. **查最近变更**——git diff、最近提交、依赖/配置变化、环境差异
4. **追溯上游**——为什么走到这个状态：表象 → 直接原因 → 本地根因 → 系统根因 → 过程根因。停在"哪里报错"不够

### 阶段 2：提出根因假设

基于证据的假设（不是猜测），并说明该假设如何解释全部症状。

### 阶段 3：最小修复

- 先写复现测试（确认测试能捕获问题）——修 bug 必须先有复现测试
- 修复根因，不修报错行而不追问为什么

### 阶段 4：验证

- 复现测试通过 + 全量测试无回归
- 用 verify_gate 跑测试套件；complete_step 记录证据

## 反模式

- 直接 patch 报错行（表象修复）
- 同一个错误反复修 3+ 次 → 架构问题，停下来重新调查
- 跳过复现直接猜根因
