# 接收代码审查反馈

## 何时使用

- **必须**：收到代码审查反馈（review 子代理、用户或外部审查者），在动手实现前先调用本技能
- 反馈越模糊、越可疑，越要用——技术评估，不是情绪表演

## 核心原则

**先验证，再实现；先澄清，再假设；技术正确性优先于社交舒适。**

## 6 步响应模式

1. **读**：完整读完反馈，不急于反应
2. **理解**：用自己的话复述要求（不清楚就问）
3. **验证**：对照代码库实际检查（grep / read_file / git diff）
4. **评估**：对**当前代码库**是否技术成立
5. **回应**：技术性确认，或基于推理的反驳
6. **实现**：逐项实现，每项单独测试

## 禁止的回应

**绝不：**
- "你说得完全对！"（表演性同意）
- "好观点！/ 极好的反馈！"（表演性附和）
- 未经验证就说"我马上改"

**应该：**
- 复述技术需求
- 提出澄清问题
- 错误时用技术推理反驳
- 直接开始验证/工作（行动 > 空话）

## 处理模糊反馈

任一反馈项不清楚 → **停下，先澄清，不实现任何项**——多项反馈可能相互关联，部分理解 = 错误实现。

示例：反馈 1-6 项，只懂 1/2/3/6：
- ❌ 先实现懂的，稍后再问 4/5
- ✅ "我理解 1、2、3、6；4 和 5 需要澄清后才能继续。"

## 外部审查者的反馈

实现前逐条检查：
1. 对**本代码库**技术正确？
2. 会破坏现有功能？
3. 当前实现是否有其存在原因？
4. 所有平台/版本都成立？
5. 审查者是否了解完整上下文？

看似错误 → 用技术推理反驳；无法快速验证 → 明说"没有 X 我无法验证，是否调查/询问/继续？"；与用户先前决策冲突 → 先与用户讨论。

## YAGNI 检查

审查者建议"正规实现"某个功能时：先 grep 代码库确认实际使用——
- 未被使用 → "这个接口没被调用，删掉（YAGNI）？"
- 确实使用 → 再正规实现

## 实现顺序（多项反馈）

1. 先澄清所有不清楚项
2. 按顺序实现：阻塞问题（崩溃/安全）→ 简单修复（拼写/import）→ 复杂修复（重构/逻辑）
3. 每项修复单独测试
4. 最终验证无回归（verify_gate / 全量测试）

## 何时反驳

- 建议会破坏现有功能
- 审查者缺少完整上下文
- 违反 YAGNI（未使用功能）
- 对当前技术栈不正确
- 存在遗留/兼容性原因
