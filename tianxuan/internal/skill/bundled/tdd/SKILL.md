# 测试驱动开发（TDD）

## 何时使用

- **必须**：任何新功能、bug 修复、重构、行为变更——动手前先调用本技能
- 可与用户确认后跳过：一次性原型、纯生成代码、配置文件

## 铁律

```
无失败测试，禁止写产品代码。
```

- 提前写的产品代码**必须删除重来**——不能留作参考、不能边写测试边"调整"
- "就这一次跳过 TDD" 是合理化借口，停下来

## 红绿重构循环

1. **RED**：先写失败测试（精确断言目标行为）
2. **验证失败**：用 verify_gate 或 bash 运行测试，确认测试确实失败——失败原因 = 目标行为未实现。没看到失败，就不知道测试是否在测对的东西
3. **GREEN**：写最小实现——只够让测试通过（YAGNI）
4. **验证通过**：重跑测试全绿、无回归
5. **REFACTOR**：在测试保护下清理实现
6. 每步用 complete_step 记录证据（测试命令输出 / diff / 文件路径）

## 反模式

- 先写实现再补测试（测试会迁就实现）
- 测试从不失败（断言太弱，测不到目标行为）
- 一次写大量产品代码（应随测试逐步生长）
